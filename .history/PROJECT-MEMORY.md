# Project Memory

## Context checkpoint lifecycle

- **Current rule:** The `checkpoint` extension tool and manual `/checkpoint` command copy the active compaction-aware LLM messages as structured context, remove the incomplete checkpoint tool call when applicable, and run two chained future-self passes: factual extraction followed by review/correction combined with final checkpoint generation. Each pass retries whitespace-only model output up to three times after its initial request, while provider errors, aborts, malformed responses, and explicit error stop reasons fail immediately. After exhaustion, the thrown stage-specific error is retained as a model-visible failed tool result. The manual command waits for Pi to become idle and uses safely defaulted progress fields. Both paths hand only the final durable checkpoint to Pi's compaction lifecycle and start one hidden continuation turn after successful manual or automatic extension compaction; when the public context estimate is at or below Pi's default keep-recent budget, they skip compaction as a successful no-op and queue the same continuation. The exact `Nothing to compact (session too small)` callback is also benign. Checkpoint compaction uses Pi's native retained-tail boundary so it does not discard more visible history than native `/compact`. Pi 1 automatic failures arrive through `session_compact_failed`; non-aborted failures retain one pending checkpoint until `agent_settled` and expose `/checkpoint_context_recover`, which is only for that recovery case. Only the user-invoked recovery command may create a replacement session.
- **Why:** Structured messages preserve conversational continuity better than a flattened transcript, while truncating the in-flight call avoids malformed nested provider context. Bounded retries recover transient empty provider responses without hiding persistent failures or retrying non-retryable errors. Pi's extension-originated `sendUserMessage()` skips slash-command expansion, `sendMessage()` with `triggerTurn` is the public continuation path, and `newSession()` is restricted to command contexts to avoid deadlocks.
- **Authority:** `extensions/context-checkpoint.ts`, `src/checkpoint-core.ts`, and the task records for this feature.

## Checkpoint concurrency and input delivery

- **Current rule:** Pi tool lifecycle events are tracked so `checkpoint` is blocked while another Pi tool or subagent execution is active; active tools are never aborted. Input events that Pi delivers from interactive or RPC sources during checkpoint generation/compaction are batched and released exactly once at a terminal lifecycle boundary. Manual compaction releases after its public completion callback; Pi 1 automatic compaction success or failure releases after `agent_settled`; session shutdown releases old-instance input before teardown. Pi may reject RPC prompts before `input` while compaction is locked, and interactive input queued by Pi may be released by Pi itself, so those cases are outside the extension's unified batch guarantee. Automatic failures use `session_compact_failed` and do not trigger a duplicate manual fallback. Detached processes and slash commands are outside scope.
- **Why:** Prevents checkpoint context from racing with active tool results while preserving user input that reaches the extension, without cancelling useful work or awaiting a release path inside lifecycle handlers.
- **Authority:** `extensions/context-checkpoint.ts`, `README.md`, and Pi's public extension lifecycle API.
- **History:** [2026-10-02 Pi 1 migration](2026-10-02-pi-1-migration.md), [Gate active work and queue input during checkpoint processing](2026-09-11-queue-input-during-checkpoint.md)
- **Revisit:** Revisit when Pi exposes a pre-lock input interception hook or a public automatic-compaction completion event, and run provider-backed interactive/RPC testing when authenticated testing is available.

## Checkpoint timing

- **Current rule:** The LLM-facing checkpoint guidance treats `checkpoint` as an amortization boundary between two substantial phases: substantial work must already have accumulated and another substantial phase must remain. It explicitly excludes final-report checkpoints and pre-work checkpoints; context-pressure hints defer urgent calls to the next safe boundary between substantial phases when future substantial work exists.
- **Why:** Each checkpoint performs two nested LLM passes over the active context, so running it after the last substantial phase or before meaningful context exists can cost more than it saves.
- **Authority:** `extensions/context-checkpoint.ts`, `src/context-usage-hint.ts`, and `README.md`.

## Checkpoint summary model selection and settings

- **Current rule:** Immediately before checkpoint generation, resolve the model with precedence `PI_CHECKPOINT_MODEL → project → global → active`; only an available authenticated candidate is accepted. Persist overrides under the extension-owned `pi-context-checkpoint.endlessModel` key as `provider/model` in global or trusted-project settings. Global Default removes the global override; project Default removes the project override and therefore inherits global or active behavior. `/endless-settings` exposes the scoped model picker without changing Pi's active or default model.
- **Why:** Checkpoint summarization can use a separately configured model while preserving Pi's normal model selection and safely retaining unrelated settings fields. Project trust gating prevents untrusted project files from controlling model selection without disabling global fallback.
- **Authority:** `extensions/context-checkpoint.ts`, `src/endless-settings.ts`, `src/endless-model-selector.ts`, and `README.md`.
